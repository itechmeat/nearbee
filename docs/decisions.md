# Decisions

Taken decisions with their reasons. Reopen one only with a new fact, and record
the change here.

| id | Date | Decision | Why |
| --- | --- | --- | --- |
| D-001 | 2026-11-09 | The hackathon product is the adapter (Nearbee), not a mascot app and not single agents. Two example agents demonstrate it. | The adapter is what the market lacks (capable self-hosted agents) and what apb owners lack (a storefront and a payment rail). Rejected earlier: mascot-centric ideas and a trading voice assistant. |
| D-002 | 2026-11-09 | Name: Nearbee. NEAR-bound in name only; code names are neutral (`Market`, `Runner`, `Listing`). | Owner's choice among 60 candidates. "NearBee" also belongs to a dormant 2018 to 2022 beacon-marketing SDK by Beaconstac and a Swedish coupons app; no conflict in AI or crypto. `nearbee.near` is taken by someone else and is not needed. |
| D-003 | 2026-11-09 | **Rust** for the adapter (cargo workspace; `reqwest`, `serde`, `tokio`, `clap`; `near-primitives` or `near-api` for NEP-366 signing). The demo caller may fall back to a small `near-api-js` script if Rust signing is awkward on Day 1. Supersedes the Bun + TypeScript proposal. | Owner 2026-11-09: no UI is planned, so Rust is fine ("если нет интерфейса, спокойно можно использовать Rust"). Same language as apb (Nearbee may become an apb crate or `apb market` later), NEAR's core ecosystem is Rust, the owner's agents and tooling are set up for it. |
| D-004 | 2026-11-09 | Nearbee drives apb over the REST API of `apb dashboard`, never by embedding apb. CLI calls stay for `apb decide`, `apb stats --json`, `apb runs --json` where the API lacks a route. | Language independence, one supervision surface, server-mode auth already exists. |
| D-005 | 2026-11-09 | One market agent per listing variant (SKU). | The market has one default `per_call` price per agent and no buyer-selectable plans. |
| D-006 | 2026-11-09 | Intake before start: take or decline; decline `rejected` within the first hour. Per-hire cumulative cost ceiling as the run budget plus a wall-clock limit; global loss limits. | Per-job pricing puts the cost risk on the seller; early declines are free of reputation cost and refund the buyer in full. apb's budget is a predictive stop, not a hard cap (Codex review, finding 3). |
| D-007 | 2026-11-09 | Privacy tiers plain, attested, blind; validated at publish time from apb profiles, connectors and decision providers; descriptions generated, not typed. **The attested tier's v1 evidence is run-level attestation disclosure**, labelled as such; per-response proof through the signed script step of D-008 where a playbook has one. | The listing is part of the contract; only shown claims may be promised. apb's `environment` is not a sandbox and run-level reports do not bind responses (Codex review, findings 4 and 9). |
| D-008 | 2026-11-09 | Model choice stays in apb profiles; Nearbee ships profile templates and validates them. **Approved exception**: in `doc-digest-private` the final digest generation is one bounded Cloud API call from a trusted `script` node that keeps the exact bytes and fetches the `provider_tee` response signature; the rest of the pipeline runs through profiles with run-level disclosure. No blind tier, no sandboxing in v1. | Owner 2026-11-09: a balanced promise, "good for the hackathon, no over-engineering". General CLIs hide the bytes needed for signed evidence (Codex review, idea 23). |
| D-009 | 2026-11-09 | Listings belong to the owner's market account; self-registration is used only for throwaway tests. | Self-registered agents cannot withdraw and stay out of Discover. |
| D-010 | 2026-11-09 | Tracks: `agents`, `privacy`, `business`. | See `docs/hackathon.md`. |
| D-011 | 2026-11-09 | v1 has no web UI, no webhooks, no buyer questions during a run, no owner review gates in market playbooks, no board bidding, no on-chain writes by the worker, no blind tier, no example agent C. | Five days; the risky paths come first (Codex review, section 3). |
| D-012 | 2026-11-09 | Buyer data never enters apb's learning features; market playbooks run in a dedicated apb project with discover, memory, corrections and judge-example capture off; exact settings recorded once verified. | Job Terms 7.1: use only for the job, no training. A project alone disables nothing (Codex review, finding 20). |
| D-013 | 2026-11-09 | Listing variants are **materialised** as separate apb playbook ids with fixed profile bindings and a version digest; `serve` verifies the executed playbook id and version. | The REST start has no `version` or `overrides` field (Codex review, finding 2). |
| D-014 | 2026-11-09 | The run result is a **manifest** `out/result.json` (Markdown, files, evidence, hashes, sizes) validated before submit; a missing or invalid manifest fails the hire closed. Reports and summaries are never submitted. | apb has no result contract; reports can expose internal material (Codex review, finding 14 and idea 24). |
| D-015 | 2026-11-09 | Durable hire journal with intent records before every external write, a recovery table, `hire_id` as an apb search param, `clientRequestId` on thread sends, identical resubmits. | The apb start has no caller request id; the market retries need idempotency (Codex review, finding 10). |
| D-016 | 2026-11-09 | Polling of assignments in all statuses with paging is the source of truth; acceptance is read, never inferred from `autoAcceptAt`. | The default view is `in_progress` only (Codex review, finding 11). |
| D-017 | 2026-11-09 | Listings open to A2A callers run self-contained playbooks: no questions, validated defaults or early reject. | A2A has no multi-turn (Codex review, finding 13). |
| D-018 | 2026-11-09 | **v1 pricing is the owner's explicit price and SLA per listing.** Limits are optional. The adapter protects the owner without configuration: a per-hire cost ceiling derived from the price (run budget plus wall-clock limit, decline with full refund on overrun) and one cheap scope check before start; both can be switched off per listing. Auto-pricing from run observations (own p90, rework reserve, decimal rounding) is v1.1. | Owner 2026-11-09: do not fuss over limits; Nearbee cannot know what an arbitrary playbook can handle, only its author can. apb exposes medians and ranges only (Codex review, findings 7, 18, 19). |
| D-019 | 2026-11-09 | Owner-provided items (accounts, keys, go-aheads) are tracked in `docs/owner-checklist.md` and requested by the working agent at the plan step where each is first needed, not up front. | Owner 2026-11-09: "запиши это в требования проекта, мы это сделаем в процессе, пусть агент напомнит мне когда придет время". |
| D-020 | 2026-11-09 | Work is organised in six stages (`docs/stages.md`), each one OpenSpec change on the project schema `openspec/schemas/nearbee` and one pull request, through the cycle of `docs/process.md`: artifacts reviewed by another model family, implementation by a separate coding agent, acceptance and the quality cycle (native gate, OCR, cross-family review, security and test audits, security review, final review) by the integrator. | Owner 2026-11-09: every stage built in OpenSpec on a non-default setup, code by another agent, the coordinating agent accountable for the result and for the review cycle used in the owner's other projects. |
| D-021 | 2026-11-09 | Implementers are Opus subagents of the integrator; the integrator merges a stage on a clean cycle and green native gate without asking; the public repository https://github.com/itechmeat/nearbee was created by the owner the same day, so stages land as pull requests there. Project skills live in `.agents/skills` (`.claude/skills` is a symlink): market, NEAR AI Cloud, near-api-js, near-cli-rs, rust-skills, OpenSpec workflow skills (`.agents/skills/NOTICE.md`). | Owner answers 2026-11-09; skills layout as in near/intents. |
